## 포트폴리오 탭

### 요약 카드 (5개)

| 카드 | 내용 |
|------|------|
| 총 매입금액 | 보유 잔고 × 평균매입가 합계 |
| 총 매입금액(현금) | 위 금액 중 **현금으로 매입한 몫**만. 분배금 재투자분 제외 |
| 총 평가금액 | 보유 잔고 × 현재가(`t_stock_amt` 최신값) 합계 |
| 총 평가손익 / 수익률 | 평가금액 − 총 매입금액, 수익률(%) |
| 총 평가손익 / 수익률(현금) | 평가금액 − 총 매입금액(현금), 수익률(%) |

현금 기준 카드 2개는 본문 아래에 `분배금 재투자 {금액} 제외` 를 작은 회색 글씨로 붙여
어느 금액이 빠졌는지 드러낸다 (금액은 `총 매입금액 − 총 매입금액(현금)`, 두 카드 동일).

**현금 기준 카드가 왜 따로 있나** — 분배금으로 재투자한 돈은 이미 이 투자에서 나온 수익이다.
내 주머니에서 실제로 들어간 돈(현금)만 원금으로 잡으면 진짜 수익률이 보인다.

`총 매입금액(현금)` 은 **잔고 비례**로 계산한다. 매도가 있어도 `총 매입금액` 과 기준이 같아
두 카드를 그대로 비교할 수 있다 (계산식은 `stock_task.md` 참고).

### 보유 종목 테이블

- 컬럼: 종목코드 / 종목명 / 구분(주식·ETF) / 잔고 / 평균매입가 / 현재가(전일대비) / 매입금액 / 평가금액 / 평가손익 / 수익률
- **계좌별로 묶어** 보여준다. 계좌 헤더 행 구성 (모든 계좌 동일):

  | 위치 | 내용 |
  |------|------|
  | 좌측 | `{계좌번호} ({계좌명})` |
  | 좌측 이어서 | `분배금 재투자 {금액} 제외 · 현금 {현금매입액} → {현금기준 손익}({수익률})` |
  | 우측 | `매입 {금액}` · `평가 {금액}` · `{손익}({수익률})` |

  좌측 현금 기준 수치는 요약 카드의 현금 카드 2개와 같은 기준이다 (`total_buy_amount_cash` 합계).
  재투자가 없는 계좌도 `분배금 재투자 0원 제외` 로 똑같이 표기해 계좌끼리 바로 비교된다.
- 평가금액 큰 순으로 정렬
- 행 클릭 → 해당 종목 일별 주가 차트 표시 (토글)
- 행 호버 → 종목별 매입 내역 툴팁 (매입일 / 수량 / 매입가 / 현재가 / 수익률)
- **네이버 주가 가져오기** 버튼: `t_stock_list default_yn='Y'` 전체 종목 대상 모바일 JSON API 증분 수집 → `t_stock_amt` 저장
- **네이버 금융 →** 링크: 선택 종목 네이버 금융 페이지 새 탭 오픈
- 코스피·코스닥 지수 실시간 조회 결과를 헤더에 표시

### 일별 주가 차트 (종목 선택 시)

- Recharts LineChart — `t_stock_amt` 종가 데이터 사용
- 기간 필터: 1개월 / 3개월 / 6개월 / 1년 / 전체
- 평균가 기준선(ReferenceLine) 표시
- 차트 하단 일자별 주가 테이블 (날짜 / 종가 / 전일대비 / 등락률, 최대 높이 480px 스크롤)

## 매입/매도 모달

`[+ 매입/매도 내역 추가]` → 위쪽 **입력 폼**, 아래쪽 **기존 거래 내역 목록**을 한 모달에 담는다.

### 입력 폼

2줄 4칸 그리드로 접어 팝업 높이를 줄였다.

| 줄 | 칸 (grid-cols-4) | 입력 항목 | 설명 |
|----|------------------|-----------|------|
| 1 | 1 | 일자 | `<input type="date">` 달력 선택 (기본값: 오늘) |
| 1 | 1 | 자금 구분 | **현금(1) / 분배금(2)** 라디오 버튼 |
| 1 | 2 | 계좌 | `my_account` 목록 select (기본값: 첫 계좌) |
| 2 | 2 | 종목 | `t_stock_list` DB 검색 (200ms 디바운스). 빈 값 입력 시 `default_yn='Y'` 인기 종목 최대 20개 표시. 선택 후 칩 표시 |
| 2 | 1 | 단가 | 숫자 입력 (원) |
| 2 | 1 | 수량 | 숫자 입력 (주). **양수 = 매입, 음수 = 매도** |

아래에 `총 금액: 단가 × 수량` 미리보기 한 줄.

- 매입/매도는 별도 버튼 없이 `qty` 부호로 정한다 (`cnt` 는 부호에서 파생 저장)
- 자금 구분 칸은 **매도일 때도 자리를 지킨다** — 라디오 대신 `매도 — 해당 없음` 안내를 띄운다.
  칸을 없애면 옆의 계좌 칸이 밀려 레이아웃이 튄다
- 수량 부호 규칙은 수량 입력 라벨(`수량 (주, 매도 시 음수)`)이 설명한다. 별도 안내 박스는 두지 않는다
- 저장 → `my_stock` INSERT + `my_account_info` 에 대응 출금(매입)·입금(매도) 행 자동 생성
- 분배금으로 매입해도 **출금 행은 그대로 생성**한다. 분배금도 계좌에 들어온 돈이라 계좌 잔액에서는 똑같이 빠져나간다.
  비고만 `매입(분배금): {종목코드}` 로 구분해 적는다
- 취소 → 폼 초기화

### 기존 거래 내역 목록 (모달 하단)

| 컬럼 | 내용 |
|------|------|
| 일자 / 계좌 / 종목 / 구분(매입·매도) / 자금(현금·분배금) / 수량 / 단가 / 금액 | 읽기 |
| 수정 | 그 행의 값을 위 입력 폼에 채워 **수정 모드**로 전환 |
| 삭제 | `confirm` 후 `my_stock` 레코드 삭제 |

- **위 폼에서 고른 계좌의 거래만 보여준다.** 계좌 select 를 바꾸면 목록도 따라 바뀐다
  (제목 옆에 `{계좌번호} · {건수}건` 표기, 해당 계좌에 거래가 없으면 "이 계좌의 거래 내역이 없습니다.")
- 최신 거래 상단, 스크롤 목록
- 수정 모드에서는 모달 제목이 `매입/매도 내역 수정` 으로 바뀌고, 수정 중인 행이 목록에서 강조된다
- 수정 모드에서 `[새로 추가]` 를 누르면 빈 추가 폼으로 되돌아간다
- **거래를 수정·삭제해도 저장 때 자동 생성된 `my_account_info` 행은 따라 바뀌지 않는다.**
  계좌 입출금은 `계좌 내역` 탭에서 따로 맞춘다

## 적립 탭 — 주식모으기

나무증권 주식모으기로 매일 자동 매수한다. **체결을 매일 넣을 수 없어** 가끔
`보유수량 · 평균매입가 · 계좌잔액` 세 값만 넣고 구간 매입을 역산한다.

### 왜 역산이 되는가

평균 매입가는 `총 매입원가 ÷ 보유수량` 이라 총 원가를 복원할 수 있다.
두 스냅샷의 차이가 그 구간의 매입이다 — 근사치가 아니라 **정확한 값**이다.

```
구간 매입금액 = (수량₂ × 평균가₂) − (수량₁ × 평균가₁)
구간 매입수량 = 수량₂ − 수량₁
```

### 기산일 분할

분배금 대상 수량은 **기산일 하루**(`ACCUM_BASE_DAY`, 매월 13일)만 본다.
그 경계만 맞으면 분배금 계산이 어긋나지 않으므로, 구간이 기산일을 가로지를 때만 쪼갠다.

| 상황 | 생성 행 |
|------|---------|
| 구간이 기산일을 안 넘음 | **1행** — 입력일 날짜 |
| 구간이 기산일을 넘음 | **2행** — 기산일까지 몫은 `기산일` 날짜로, 나머지는 `입력일` 날짜로 |

수량은 구간의 **실제 거래일 수**에 비례 배분한다 (`t_stock_amt` 를 쓴다 — 휴일표가 필요 없다).
기산일 판정 자체는 **달력 기준**이다 — 거래일에서 찾으면 휴장일·미래 구간을 놓친다.

**주가가 아직 안 들어온 구간은 평일 수로 대신한다** (`split_basis='weekday'`, 표에 `추정` 배지).
달력일로 세면 주말·공휴일을 거래일과 똑같이 세어 휴일이 몰린 구간이 과대평가된다 —
실제로 10/02~10/22 구간이 달력일 11/20 으로 13주/11주가 나왔는데, 거래일로는 6/13 이라
11주/13주가 맞았다. 평일 수로 바꿔 12주/12주까지 좁혔다.

평일 수도 공휴일은 못 걸러낸다. **「네이버 주가 가져오기」로 그 구간 주가를 먼저 수집하면
실제 거래일로 정확히 쪼갠다.**

### 잔액 검증 — 매일 안 넣어도 예수금이 맞는 이유

```
예상 잔액 = 직전 잔액 + 구간 입금 − 구간 매입금액
차이 = 실제 잔액 − 예상 잔액    →  0이 아니면 기록에 없는 입출금이 있다는 뜻
```

차이를 `잔액 조정` 행 한 줄로 흡수한다. **스냅샷을 넣을수록 예수금이 저절로 맞아간다.**

### 자금 구분 안분

연금저축은 분배금과 자동이체(현금)가 섞여 들어온다. 계좌 내역에 이미 구분돼 있으므로
**구간 입금 비율대로** 매입을 현금/분배금 두 행으로 나눈다.

- `잔액 조정` 행은 실제 입금이 아니라 보정이라 **안분 근거에서 뺀다**
- 구간에 입금 기록이 전혀 없으면 전액 분배금으로 본다 (적립 재원이 분배금 재투자라는 전제).
  **자동이체를 계좌 내역에 넣지 않으면 현금분이 분배금으로 잡힌다** — 생성될 내역 표의 `구분` 열로 확인한다

### 매도는 역산할 수 없다

평균 매입가는 매도해도 바뀌지 않아 수량만 줄어든다. 스냅샷에서 수량이 줄면 **막고 안내**한다 —
매도는 매입/매도 모달에서 따로 넣어야 한다.

### 입력 폼

안내 문구를 두지 않는다. 라벨만으로 충분하고, 설명이 길면 입력 영역이 밀린다.

| 줄 | 칸 (grid) |
|----|-----------|
| 1 | 적립 종목(2칸) · 계좌 · 기준일 — `grid-cols-4` |
| 2 | 보유 수량(주) · 평균 매입가(원) · 계좌 잔액(원) — `grid-cols-3` |

종목 검색 드롭다운은 입력칸이 좁아 종목명이 잘리므로 `min-w-[26rem]` 로 칸보다 넓게 띄운다.

- **종목은 여기서 바꾼다.** 기본값은 `ACCUM_STOCK_CODE`, `t_stock_list` 검색으로 교체 가능.
  스냅샷 계산(`planSnapshot`)이 원래 종목을 인자로 받으므로 한 종목에 묶어둘 이유가 없다
- **금액 칸은 천단위 구분자를 보여준다.** `type="number"` 로는 안 돼서 `type="text" inputMode="numeric"` 로
  받고 숫자만 걸러 저장한다 (`digits`/`comma` 헬퍼)
- 계좌 잔액은 비워도 된다 — 그러면 잔액 보정을 건너뛴다
- **기준일은 오늘까지만** 넣을 수 있다 (입력칸 `max` + 서버 검증). 스냅샷은 '그날 실제로 이랬다' 는
  기록이라 미래 날짜가 성립하지 않고, 막지 않으면 아직 오지 않은 구간을 평일 수로 추정해
  그럴듯한 거짓 수치가 나온다
- 한도·기산일·자동이체는 환경 변수 전용이다 (CLAUDE.md 설정 UI 는 읽기 전용 원칙)

### 미리보기

**표 하나로만** 보여준다. 요약 칸이나 설명줄을 두지 않는다 — 숫자가 표에 그대로 있다.

| 행 | 내용 |
|----|------|
| 본문 | 생성될 매입 — 일자(기산일 배지) · 구분(현금/분배금) · 수량 · 단가 · 금액 |
| 합계 | 구간 수량 · 구간 단가 · 구간 매입금액 |
| 잔액 조정 | 0이 아닐 때만 (부호별 색) |

막히는 경우(매도 등)에는 표 대신 사유만 붉게 띄운다.

환경 변수가 안 읽혔을 때만 (`ACCUM_STOCK_CODE`·`ACCUM_ACCOUNTS` 가 빈 값) 빠진 변수 이름과
해결법을 붉은 박스로 띄운다. `next.config.ts` 의 dotenv 가 서버 기동 시 한 번만 읽어서,
값을 추가하고 재시작하지 않으면 조용히 비는 함정이 있다.

### 분배금 기산일 정리

**적립 종목** 기준이다. 최근 12개월의 기산일(매월 `ACCUM_BASE_DAY`)을 월별로 생성하고,
각 기산일의 적립 종목 보유수량·스냅샷 유무를 보여준다.
그 달에 적립 종목의 분배금이 등록돼 있으면 지급기준일·실지급일·주당 분배금을 덧붙인다.

| 열 | 내용 |
|----|------|
| 기산일 | 매월 `ACCUM_BASE_DAY`. 아직 안 왔으면 `예정` |
| 보유수량 | 그 날짜까지 누적된 **적립 종목** 수량 |
| 스냅샷 | 그 날짜에 적립 종목 매입 행이 있는가 |
| 지급기준일 · 실지급일 · 주당 분배금 | 적립 종목 분배금이 등록된 달만 |

기산일을 `t_etf_dividend` 에서 뽑으면 안 된다. 적립 종목에 분배 이력이 없을 때 표가 통째로
비고, **재원 종목(`498400`)의 기준일이 섞여 들어와 적립 종목 수량과 짝이 안 맞는다.**
실제 분할에 쓰는 기산일도 분배금 기록이 아니라 `ACCUM_BASE_DAY` 다.

**기산일에 스냅샷을 한 번 찍으면 그 달 분배금 수량 오차가 0이 된다.**

## 투자 이력 탭

전용 테이블 **`my_history`** 를 쓴다. 쇼핑 참고 자료(`my_shopping`)에서 분리됐다.
상단 콤보박스 + 전체 너비 본문 구조는 그대로다.

| 항목 | 컬럼 | 내용 |
|------|------|------|
| 구분 | `category` | **주식(`stock`) / 연금(`pension`)** — 등록·수정할 때 고른다 |
| 등록일자 | `t_date` | `<input type="date">`, 기본값 오늘 |
| 제목 | `title` | |
| 내용 | `contents` | `RichEditor` HTML |

- 상단 바에 **구분 필터** (`구분 전체` / 주식 / 연금). 필터를 걸어둔 채 `[+ 추가]` 하면 그 구분으로 시작한다
- **구분을 바꾸면 본문도 따라 바뀐다.** 보던 글이 그 구분에 있으면 유지하고, 없으면 첫 글로 넘어간다.
  그 구분에 글이 없으면 본문도 비운다 — 본문을 전체 목록이 아니라 **걸러진 목록**에서 고르기 때문이다
- 목록은 `t_date` 내림차순 — `{등록일자} · {구분} · {제목}`
- 구분값은 `app/assets/stock/history-categories.ts` 에 모아 두고 서버에서도 검증한다
- 첨부파일은 쓰지 않는다

**`my_shopping` 의 `category` 와 다르다.** 그건 어느 메뉴 글인지 가르는 값이었고,
여기 `category` 는 **글의 성격**이라 화면에서 직접 고른다.

------|------|
| 상단 바 | 구분 이름 + **목록 콤보박스**(`{등록일} · {제목}`) + 건수 + 조작 버튼 |
| 본문 (보기) | 제목 + 우측에 구분·등록일 + 내용 HTML 렌더 |
| 본문 (입력) | 제목(3칸) + 구분(1칸, 읽기 전용) + 내용 `RichEditor` (minHeight 470) |

**다루는 항목은 4개뿐** — 구분 / 제목 / 등록일 / 내용.

- **첨부파일 기능은 넣지 않는다.** 쇼핑 참고 자료의 `FileDropZone`·`FileList` 를 쓰지 않는다
- 구매처·제품가격은 쇼핑 전용이라 이 화면에서 안 쓴다 (`NULL` 로 남는다)
- **구분은 화면에서 고르지 않는다.** 이 탭에서 쓴 글은 항상 `주식 투자` 다.
  값은 `app/shopping/ref-groups.ts` 의 `REF_GROUPS` 에서 온다
- 제목이 비면 저장하지 않고 알린다
- 추가 모드에서는 콤보박스 자리에 `새 항목 작성 중` 이 뜬다 (잘못 눌러 작성 중인 글이 날아가지 않게)
- 저장하면 **그 항목이 선택된 상태로** 돌아온다. 삭제하면 첫 항목으로 떨어진다
- 선택 항목은 id 로만 들고 목록에서 끌어온다 → 재조회해도 선택이 유지된다

## 분배금 수익율 팝업

보유 종목 표에서 종목을 고르면 `[분배금 수익율 조회]` 버튼이 뜬다 —
**`t_etf_dividend` 에 분배금 이력이 있는 종목만**. 고른 종목으로 팝업이 열린다.

특정 종목 전용이 아니다. 버튼 노출 조건은 `getDividendStockCodes()` 가 돌려주는 목록이고,
팝업 제목·데이터·`[계좌 입금 내역 재생성]` 모두 그 종목 기준이다.

| 영역 | 내용 |
|------|------|
| 헤더 링크 | 종목명 브랜드로 운용사를 가려 **운용사 분배금 공시 페이지**를 새 탭으로 연다 (아래 표) |
| 요약 카드 | 최근 분배율 / 월평균 분배율(**최근 12개월 평균**) / 연환산 수익률(월평균 × 12) |
| 이번 달 분배금 카드 | 이번 달 지급 이력이 있으면 **확정**(실적치), 없으면 **추정** |
| 지급 이력 테이블 | 지급기준일·실지급일·분배율·분배금액·과세표준액 + 계좌별 분배금 열 + 보유 잔고·합계 |

### 운용사 공시 링크

분배금을 손으로 확인·입력할 때 공시 원문을 바로 열 수 있게 헤더에 링크를 둔다.
운용사 판별은 수집기(`collector/etf-dividend/db.py` `BRAND_TO_HOUSE`)와 같은 브랜드 기준이고,
주소도 수집기가 긁는 페이지와 같다. 운용사 페이지는 종목코드로 바로 가는 주소가 없어 **전 종목 목록**이 열린다.

| 브랜드 | 링크 라벨 | 주소 |
|--------|----------|------|
| KODEX | 삼성 분배금 공시 ↗ | `samsungfund.com/etf/product/distribution.do` |
| TIGER | 미래에셋 분배금 공시 ↗ | `investments.miraeasset.com/tigeretf/ko/distribution/overall/list.do` |
| RISE · KBSTAR | KB 분배금 공지 ↗ | `kbam.co.kr/support/notice` |
| 그 외 | 분배금 검색 ↗ | 네이버 검색 `{종목명} 분배금` |

### 이번 달 분배금 카드 — 확정 / 추정

**이번 달 지급 이력이 있으면 그 실적치로 고정하고, 없을 때만 추정한다.**
이미 확정된 달에 굳이 추정치를 보여줄 이유가 없다.

판정: `divHistory` 에 `ref_date` 의 `YYYY-MM` 이 오늘과 같은 행이 있는가.
제목 옆 배지로 어느 쪽인지 드러낸다 (`확정` 주황 / `추정` 회색).

두 경우 모두 **5열 구조는 같고 3열의 뜻만 다르다.**

| | 확정 | 추정 |
|---|------|------|
| 제목 | `{YYYY.MM} 분배금` `확정` | `내 잔고 기준 이번 달 예상 분배금` `추정` |
| 부제 | 13일 기산 수량 × 주당 분배금 | 현재 잔고 × 당일 종가 × 월평균 분배율 |
| 2열 보유 잔고 | `qty_13th` (13일 기산) | `net_qty` (지금 시점) |
| **3열** | **주당 분배금** (`dist_amt`) | **{일자} 종가 기준** (`latest_price`) |
| 4열 | `분배금` = `dist_total` | `예상 분배금` = 잔고 × 종가 × 월평균 분배율 |
| 5열 과세표준액 | `tax_total` | 잔고 × 최근 주당 과세표준액 |
| 하단 | 지급기준일 · 실지급일 · 분배율 · 주당 과세표준 | 월평균 분배율 · 주당 과세표준 |

- 확정 값은 `getMonthlyDividendByAccount()` 결과를 그대로 쓴다 →
  **지급 이력 테이블의 그 달 계좌별 분배금과 숫자가 정확히 같다**
- 추정 값은 `getHoldings()` 의 `net_qty` 기준이라 13일 기산 수량과 다를 수 있다
- 계좌 행은 `498400` 을 보유한 계좌만 나온다

**지급 이력 테이블 우측 2개 열** — `보유 잔고` 는 그 지급기준일의 계좌별 13일 기산 수량 합계,
`합계` 는 계좌별 분배금 합계다. 두 열 모두 실적치라 위 카드의 추정치와 기준이 다르다.

### 분배금 추가

이력 테이블 위 `[+ 분배금 추가]` → 인라인 입력 폼.

| 입력 항목 | 필수 | 설명 |
|-----------|------|------|
| 지급기준일 | ✓ | `<input type="date">`. `t_etf_dividend` PK의 일부 |
| 실지급일 | | 보통 기준일 며칠 뒤 |
| 분배율(%) | | 운용사 공시값 직접 입력 (자동 계산하지 않음) |
| 주당 분배금(원) | | 정수 |
| 주당 과세표준액(원) | | 정수 |

- 종목코드는 팝업을 연 종목으로 고정된다
- **같은 지급기준일이 이미 있으면 덮어쓰지 않고 오류 메시지**를 띄운다 (PK 충돌)
- 저장 → 지급 이력과 계좌별 분배금을 함께 재조회 + **계좌 입금 내역 자동 생성**(아래)

#### 붙여넣기 입력

폼이 열린 상태에서 **영역 아무 곳에나 붙여넣으면** 한 행이 5개 칸으로 자동 분리된다.

```
26.08.14 ⇥ 26.08.19 ⇥ 1.36% ⇥ 270 ⇥ 3
   ↓          ↓         ↓      ↓    ↓
지급기준일  실지급일   분배율  분배금 과세표준액
```

| 처리 | 규칙 |
|------|------|
| 열 구분 | 탭 우선 → 없으면 2칸 이상 공백 → 그래도 없으면 단일 공백 |
| 날짜 | `YY.MM.DD` · `YYYY-MM-DD` · `YYYY/M/D` 모두 인식. 두 자리 연도는 `20YY` |
| 분배율 | `%` 제거 |
| 금액 | 콤마 제거 후 천단위 콤마 재적용 |
| 빈 칸 | 연속 탭이면 해당 항목만 비운 채 나머지 열 위치 유지 |
| 여러 행 | **첫 행만** 입력하고 "N행 중 첫 행만 입력했습니다" 안내 |
| 인식 실패 | 해당 칸을 비우고 어떤 항목인지 안내 (형식이 다른 날짜 등) |

### 분배금 수정

지급 이력 테이블 각 행 첫 열의 `[수정]` → 추가와 **같은 인라인 폼**을 수정 모드로 연다.

- 폼 제목이 `분배금 수정 — {지급기준일}` 로 바뀌고, 그 행의 5개 값이 채워진 상태로 열린다
- 수정 중인 행은 테이블에서 강조 표시
- 지급기준일도 바꿀 수 있다. 바꾼 날짜가 **다른 행과 겹치면 오류 메시지** (PK 충돌, 덮어쓰지 않음)
- 붙여넣기 입력은 수정 모드에서도 동작한다
- 저장 → 지급 이력과 계좌별 분배금을 함께 재조회 후 폼 닫힘
- 수정 모드에서 `[+ 분배금 추가]` 를 누르면 빈 추가 폼으로 전환된다
- 지급기준일을 바꾸면 **옛 날짜로 만든 계좌 입금 행을 지우고** 새 날짜로 다시 만든다

### 계좌 입금 내역 자동 생성

분배금을 추가·수정하면 `my_account_info` 에 계좌별 입금 행이 함께 만들어진다.
분배금은 실제로 계좌에 돈이 들어오는 일이라 계좌 잔액에 반영돼야 한다.

| 항목 | 값 |
|------|-----|
| 입금일자 | 분배금의 **실지급일**(`pay_date`) |
| 구분 | 입금 (`in_out = 'I'`) |
| 금액 | **13일 기산 수량 × 주당 분배금** (세전). 지급 이력 테이블의 계좌별 분배금과 같은 숫자 |
| 비고 | `분배금: {종목코드} ({지급기준일})` |
| 행 수 | 그 기준일에 수량이 있는 **계좌마다 한 행** |

- **비고가 분배금 행과 이어주는 키다.** 별도 연결 컬럼을 두지 않았다.
  저장할 때마다 이 키의 행을 전부 지우고 다시 넣어 몇 번을 눌러도 중복되지 않는다
- **화면에서 이 비고를 고치면 연결이 끊긴다** — 다음 수정 때 옛 행이 남는다
- **실지급일이 비어 있으면 입금 행을 만들지 않는다** (넣을 날짜가 없다). 기존 행이 있으면 지우기만 한다
- 세금은 빼지 않는다. 과세표준액은 지급 이력 테이블에서 따로 본다

#### `[계좌 입금 내역 재생성]` 버튼

지급 이력 머리말 우측. 등록된 분배금 **전체**에 대해 입금 행을 다시 만든다.

- 이 기능 이전에 등록한 분배금에 입금 행을 소급으로 넣을 때 쓴다
- 비고 키로 지우고 다시 넣으므로 여러 번 눌러도 중복되지 않는다
- **이 기능 이전에 손으로 넣은 분배금 입금 행은 비고가 달라 남는다** — 그건 직접 지워야 이중 계상이 안 된다

### 주가 자동 수집 (Naver 모바일 JSON API)

**2026-09: 구 `finance.naver.com/item/sise_day.naver` 가 HTTP 410 Gone 으로 폐지됐다.**
`m.stock.naver.com/api/stock/{code}/price` 로 옮겼고, EUC-KR 디코딩과 HTML 파싱은 사라졌다.

```
GET https://m.stock.naver.com/api/stock/{종목코드}/price?pageSize=60&page={N}
```

- 1페이지 = **60영업일**. `pageSize` 를 100 으로 올리면 빈 응답이 온다
- 당일 데이터 재수집을 위해 오늘 날짜 레코드를 먼저 삭제 후 수집
- 기존 데이터 있으면 2페이지(120영업일), 없으면 5페이지(300영업일)
- 3페이지씩 병렬 요청(배치) → 기존 최신 저장일 도달 시 수집 중단 (증분 방식)
- 수집 대상: `t_stock_list default_yn='Y'` 전체 종목
- **전일비 부호는 값에 들어 있다** (`"-11,000"`) — 구 파서처럼 `em` 태그 class 로 추론하지 않는다
- 등락률은 네이버 공시값(`fluctuationsRatio`)을 쓰지 않고 **직접 계산**한다 (아래 참고)
- `t_stock_amt(e_date, stock_code)` PRIMARY KEY 기준 UPSERT

**등락률을 직접 계산하는 이유** — 이미 쌓인 데이터가 `전일대비 ÷ 전일종가 × 100` 으로
계산된 값이라 기준을 맞춘다. 삼성전자·KODEX 2종 180행으로 대조한 결과 네이버 공시값과
**차이가 없어** 전환 경계에 단절이 생기지 않는다.

**쓰지 않는 대안** — `api.stock.naver.com/chart/domestic/item/{code}/day` 는 전일대비·등락률이
없고 당일 거래량이 어긋난다 (2026-09-21 삼성전자: 22,223,579 vs 정상 33,876,593).

### 분배금 공시 수집

`collector/etf-dividend/` — `t_stock_list` ETF 를 운용사 공시에서 수집한다.
GitHub Actions 로 **매일 18:00 KST** (`--apply --insert-months 2`).
자세한 내용은 그 폴더의 `README.md` 참고.

**분배금의 정답은 운용사 공시다.** 수동 입력 21건과 공시는 주당분배금이 매월 일치하고
지급기준일만 3~5일 달랐다. 2026-10 에 `(종목코드, 연월, 주당분배금)` 으로 짝지어
**20건을 공시 기준일로 옮겼다** (498400 9월: `2026-09-10` → `2026-09-15`, 분배율 1.42 → 1.45).

이때 계좌 입금 행의 비고 키도 바뀌어 옛 키 행 12건을 지우고 다시 만들었다 (합계 동일).

| 운용사 | 원천 | 상태 | 한계 |
|--------|------|------|------|
| 삼성 KODEX | 엑셀다운받기 (상장이후, 2,225행) | 동작 | 레거시 BIFF 라 `xlrd` 필요 |
| KB RISE | 공지 게시글 본문 표 | 동작 | 금액이 "예상분배금"(확정 아님), 보유 `0094M0` 은 최근 공지에 없음 |
| 미래에셋 TIGER | 엑셀다운로드 (HTML 표) | 부분 | 화면에 걸린 기간만(34행) → 과거 소급 불가, 종목코드 열 없어 종목명 매칭. GitHub 러너에선 버튼이 안 보여 실패 (해외 IP 차단 추정) |

운용사별로 따로 수집해 한 곳이 실패해도 나머지는 반영한다. 실패는 Actions 주석(`::warning::`)으로만 남기고 작업은 성공 처리한다.
모든 운용사가 실패하면 DB 반영 없이 작업을 실패(exit 1)로 끝낸다.
GitHub 러너에서는 현재 세 곳 모두 막혀 있다 (미래에셋 301, 삼성·KB 접속 타임아웃).

**13일 기산이 이제 맞다** — `getMonthlyDividendByAccount` 의 "해당 월 13일까지" 규칙은
공시 기준일 15일(월중배당)에 대한 **T-2 결제일**이라 앞뒤가 맞는다.
이관 전 기준일(10일)에서는 기준일 뒤 수량을 세는 셈이었다.
단 `13` 은 하드코딩이라 **월말배당 ETF(기준일 30일)에는 맞지 않는다.**

### 스케줄 자동 실행

- Vercel Cron: 매일 09:30 UTC (한국 시간 18:30 KST)
- 엔드포인트: `GET /api/cron/stock-sync`
- `Authorization: Bearer {CRON_SECRET}` 또는 `?secret={CRON_SECRET}` 파라미터로 인증
- `t_stock_list default_yn='Y'` 전체 종목 자동 수집
- 주가 수집 뒤 **분배금 → 계좌 입금 행도 매일 다시 맞춘다** (`syncAllDividendDeposits`).
  분배금은 화면·수집기 양쪽에서 들어오는데 입금 계산은 `lib/dividend-deposits.ts` 한 곳에만 둔다
- 응답: `{ ok, synced, deposits, at }`

> **Vercel 은 `CRON_SECRET` 환경 변수가 등록돼 있을 때만** `Authorization` 헤더를 주입한다.
> 누락되면 cron 이 호출은 되지만 401 로 떨어져 수집이 조용히 멈춘다.
> 그래서 401 응답에 사유(`reason`)를 담고 서버 로그에도 남긴다.
> `t_stock_amt.created_at` 이 스케줄 시각과 전혀 다른 시각들로 흩어져 있으면
> cron 이 아니라 화면 버튼으로만 모이고 있다는 뜻이다.

### 현재가 기준

- 현재가는 `t_stock_amt` 테이블의 최신 저장가(`latest_price`) 기반
- 전일 종가(`prev_price`)는 `t_stock_amt` 역순 정렬 2번째 레코드
